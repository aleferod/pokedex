# GenAI exercise

This document covers two things. First, the GenAI exercise from the brief: the prompt I'd use to generate a Task Management REST API, the code it produced, and how that output was validated and corrected. Second, an honest account of how this Pokédex API was built with AI, including where the AI was wrong.

## 1. The prompt

This is the exact prompt, written to be reused as is. Every requirement in it can be checked, so the output can be validated against it item by item (section 3).

````text
You are a senior Java backend engineer. Generate a complete, production-quality Task Management
REST API as a standalone Maven project. Write real, compiling code: no placeholders, no TODOs.

## Stack (use exactly these)
- Java 21, Spring Boot 4.1.1 (spring-boot-starter-parent), Maven.
- Spring Web MVC, Bean Validation, Spring Data JPA, Spring Security OAuth2 Resource Server (JWT).
- PostgreSQL 16 with Flyway migrations; Hibernate `ddl-auto=validate` (Flyway owns the schema).
- Tests: JUnit Jupiter, Spring Boot Test, spring-security-test, Testcontainers PostgreSQL.
  Do not use H2 or any in-memory database.
- Base package: com.example.tasks. Constructor injection only. Java records for DTOs. No Lombok.

## Domain
- User: id (UUID), username (unique, 3-30 chars). Users are created elsewhere, but create the
  `users` table in the migrations.
- Task: id (UUID, generated by the server), owner (the User it belongs to, required),
  title (required, 1-120 characters after trimming), description (optional, at most 2000
  characters), status (TODO | IN_PROGRESS | DONE, default TODO), dueDate (optional ISO-8601
  date, no time part), createdAt, updatedAt, version (optimistic locking).

## Authentication and authorization
- Stateless JWT bearer tokens signed with HS256; the secret comes from the environment variable
  TASKS_JWT_SECRET (at least 32 bytes, fail at startup otherwise).
- The token's `sub` claim is the username. Resolve it to the `users` row on every request; if no
  such user exists, answer 401.
- Every endpoint requires authentication.
- A user can only read and change their own tasks. Another user's task must answer 404 (never
  403), so task ids don't reveal that the task exists.

## Endpoints (all under /api/v1/tasks, JSON)
- POST   /            create; 201 with a Location header and the task.
- GET    /            the caller's tasks, paginated: page (>= 0, default 0), size (1-100,
                      default 20); optional filters status and dueBefore (date). Order by dueDate
                      ascending with tasks without a due date last, then createdAt. Response:
                      { content, page, size, totalElements, totalPages }.
- GET    /{id}        one task; 404 if missing or not the caller's.
- PUT    /{id}        replace title, description, status and dueDate. The body must include the
                      `version` the client read; a different version answers 409.
- PATCH  /{id}/status { "status": ... } changes only the status.
- DELETE /{id}        204.
- A task response contains id, title, description, status, dueDate, createdAt, updatedAt and
  version. Never return JPA entities from controllers.

## Validation and errors
- Every error is an RFC 7807 problem detail (application/problem+json) with type, title, status,
  detail, instance, and an `errors` array of { field, message } for field-level problems.
- 400 for: blank or too long title, too long description, an unknown status value, a malformed
  date, malformed JSON, unknown JSON members, page/size out of range, and a malformed UUID in the
  path. Name the offending field in `errors`.
- dueDate must not be in the past when a task is created, or when an update changes it. An
  existing overdue task can still be edited if its due date is left unchanged. "Today" is the
  current date in UTC; inject a java.time.Clock so this is testable.
- 401 without a token or with an invalid token, 404 as above, 409 for a stale version.
- Never put stack traces or exception class names in responses.

## Code structure
- Packages: task (domain service and rules), persistence (JPA entities, Spring Data
  repositories), web (controller, request/response records, mapper, exception handler), security
  (security configuration).
- Service methods are transactional. Keep controllers thin.

## Tests (they must pass)
- Web slice tests (@WebMvcTest with jwt() from spring-security-test) covering every status code
  listed above.
- Unit tests for the service: the due-date rule (create, update with the same date, update with
  a new past date) and ownership (another user's task is not found).
- One Testcontainers integration test: create a task, list returns only the caller's tasks,
  update with a stale version returns 409, delete returns 204 and the task is gone.

## Output format
Print every file of the project with its relative path as a heading, in this order: pom.xml,
src/main/resources/application.yml, the Flyway migration(s), main code, tests. After the code,
list every assumption you made.
````

## 2. The output

The generated project is in [`docs/genai-sample/`](genai-sample/). It's a standalone Maven project (`com.example.tasks`) with its own `pom.xml`, outside the Pokédex build and packages. CI builds it and runs its tests in a separate job.

```bash
# from the repository root; needs only Docker
./scripts/mvnw-in-docker.sh -B -ntp -f docs/genai-sample/pom.xml verify
```

| Package | Contents |
|---|---|
| `task` | `TaskService` (use cases, ownership and the due-date rule), `TaskStatus`, inputs (`NewTask`, `TaskChanges`), domain exceptions |
| `persistence` | `TaskEntity`, `UserEntity`, Spring Data repositories, `TaskSpecifications` (list filters) |
| `web` | `TaskController`, request and response records, `TaskMapper`, `ApiExceptionHandler` (RFC 7807) |
| `security` | `SecurityConfig`: a stateless JWT resource server (HS256), with a Bearer entry point that answers with a problem |
| `config` | `ClockConfig`: a UTC clock that ticks in microseconds |
| `db/migration` | `V1__create_users_and_tasks.sql` |

The model also listed its assumptions, kept in [`ASSUMPTIONS.md`](genai-sample/ASSUMPTIONS.md). For example: the JWT `sub` is the username, users are provisioned elsewhere, and "today" is UTC.

**A representative excerpt:** ownership and the due-date rule, as generated. This part needed no correction.

```java
@Transactional
public TaskEntity replace(String username, UUID id, TaskChanges changes) {
  TaskEntity task = owned(username, id);            // another user's task → 404, never 403
  if (task.getVersion() != changes.version()) {
    throw new StaleTaskException(id);               // → 409
  }
  if (changes.dueDate() != null
      && !Objects.equals(changes.dueDate(), task.getDueDate())
      && changes.dueDate().isBefore(today())) {
    throw new InvalidDueDateException();            // only a *changed* due date may not be past
  }
  task.replace(changes.title().trim(), changes.description(), changes.status(),
      changes.dueDate(), Instant.now(clock));
  return task;
}

private TaskEntity owned(String username, UUID id) {
  UserEntity owner = user(username);                 // unknown token user → 401
  return tasks.findByIdAndOwnerId(id, owner.getId())
      .orElseThrow(() -> new TaskNotFoundException(id));
}
```

**Provenance.** The commits of [pull request #9](https://github.com/aleferod/pokedex-api/pull/9/commits) show exactly what the model produced and what review changed. They're squashed on `main`, but the PR keeps each one:
- the prompt was committed first, on its own
- the raw output was committed **unmodified** (`fce45e5`): not compiled, run or reviewed
- each correction is a separate `fix(genai-sample):` commit

The model was Claude (Opus 5.5, through Claude Code), the same assistant that built the Pokédex. It generated the sample in one pass from the prompt alone, without looking at the Pokédex code.

## 3. Validating the output

### Method

1. **Build** against the real Spring Boot 4.1.1 dependency tree, inside Docker.
2. **Run the generated tests unchanged.**
3. **Review against the prompt, item by item:**
   - every status code
   - every validation rule
   - ownership on every endpoint
   - no entity in a response
   - a migration that `ddl-auto=validate` accepts
   - the error format, including 401 and unexpected errors
4. **Write the edge-case tests the review calls for** before fixing anything, then check which are red: a red test is a confirmed defect, and a green one is a guard.
5. **Fix one defect per commit**, with the reason in the commit message.

### Results

- **The raw output didn't build.** Maven couldn't even read the POM. It took five fixes before the generated tests ran, and then all 19 passed.
- **Passing its own tests didn't mean it was correct.** Review added 14 tests, of which 8 were red. They exposed six more defects, plus one found by reading alone. The final sample has 33 tests, all green.

| # | Found by | What the AI produced | Correction | Why it matters |
|---|---|---|---|---|
| 1 | build | Testcontainers 1.x artifact names (`postgresql`, `junit-jupiter`) | `testcontainers-postgresql`, `testcontainers-junit-jupiter` | Boot 4 manages Testcontainers 2, so there's no version for the old names and the POM can't be read |
| 2 | build | Boot 3 test packages (`boot.test.autoconfigure.web.servlet.WebMvcTest`, `boot.test.web.client.TestRestTemplate`) | Boot 4 modules: `spring-boot-starter-webmvc-test`, `spring-boot-resttestclient` and `@AutoConfigureTestRestTemplate` | The tests didn't compile |
| 3 | generated tests | `spring-security-test` only | `spring-boot-starter-security-test` | In Boot 4 the `@WebMvcTest` slice gets the security auto-configuration only through Boot's starter. Every controller test failed with no `HttpSecurity` bean. |
| 4 | generated tests | `TestRestTemplate` without its builder module | add `spring-boot-restclient` (test) | `RestTemplateBuilder` is its own module in Boot 4, so the integration test context failed with `NoClassDefFoundError` |
| 5 | generated tests | `flyway-core` only | `spring-boot-starter-flyway` | **A production defect.** Boot 4's Flyway auto-configuration is a separate module, so no migration ran, `ddl-auto=validate` found no `tasks` table, and the application could never start. |
| 6 | review | deprecated starters `spring-boot-starter-web` and `-oauth2-resource-server` | `spring-boot-starter-webmvc` and `-security-oauth2-resource-server` | They still resolve, but their POMs mark them deprecated |
| 7 | review test | a custom entry point that replaced Spring's Bearer one and built its JSON by string concatenation | delegate to `BearerTokenAuthenticationEntryPoint`, write the problem with Jackson, and add the challenge to the unknown-user 401 | RFC 6750 requires `WWW-Authenticate` on 401, and clients use `error="invalid_token"` to decide whether to refresh. The JSON had been concatenated from the raw request URI. |
| 8 | review test | no catch-all exception handler | `@ExceptionHandler(Exception.class)`: logged with its stack trace, answered with a generic 500 problem | The prompt asks for RFC 7807 everywhere and no internals. Unexpected errors fell through to Boot's default error JSON. |
| 9 | review test | `@NotBlank @Size(max = 120)` on the raw title | records strip the title in their compact constructors, before validation | "1–120 characters **after trimming**": a valid title with surrounding spaces was rejected |
| 10 | review test | `Clock.systemUTC()` | `Clock.tick(systemUTC, 1 µs)` | `createdAt` was `…665160499Z` in the POST response and `…665160Z` on a later GET, because PostgreSQL keeps microseconds |
| 11 | review test | assigned UUID ids and a primitive `@Version` | `TaskEntity implements Persistable`, new until persisted or loaded | Spring Data couldn't tell a new task from a detached one and merged it, adding a SELECT before every INSERT (3 statements per create instead of 2) |
| 12 | review test | JPQL `(:dueBefore is null or t.dueDate < :dueBefore)` | JPA Specifications, added only for the filters given | PostgreSQL can't type a null bind parameter there, so `?dueBefore=…` without `status` answered **500** |

**The secret scan also flagged the generated tests.** They hard-code two test-only HMAC signing secrets, and gitleaks' generic rule flags both. They aren't credentials, and the raw-output commit has to stay unmodified, so [`.gitleaks.toml`](../../.gitleaks.toml) allowlists exactly those two strings under `docs/genai-sample/src/test/`. I checked that any other secret placed there is still caught.

**Patterns in the mistakes:**
- **Defects 1–6 come from version drift.** The model wrote Spring Boot 3 / Testcontainers 1 idioms for a Boot 4 / Testcontainers 2 project, even though the prompt named the version. A compiler and a real dependency tree catch these immediately. A reviewer reading the code would mostly not.
- **Defects 7–12 compiled, and the generated tests passed.** They broke the prompt's own requirements or HTTP and SQL details, and only a test written for that edge case found them.
- **Defect 10 is the same mistake made while building this Pokédex** (see section 4). The model repeated it when it worked from the prompt alone, without the project's context.

### What the generated code got right

- **Ownership:** every lookup is `findByIdAndOwnerId`, so another user's task answers 404, not 403.
- **The due-date rule,** including its subtle half: an overdue task stays editable while its date is unchanged. It used an injected `Clock`.
- **Optimistic locking twice:** an explicit version check (409) plus `@Version`, with the commit-time `ObjectOptimisticLockingFailureException` also mapped to 409.
- **Bean Validation and built-in method validation** for paging, with field names in `errors`. Unknown JSON members are rejected, and unknown enum values, malformed dates and malformed UUIDs give 400s naming the field.
- **Records for DTOs,** constructor injection, no entities in responses, `open-in-view: false`, `ddl-auto: validate`, and Testcontainers instead of H2.

### Edge cases, authentication and validation in the final sample

| Concern | Behaviour |
|---|---|
| No token, bad signature, expired token | 401 problem with `WWW-Authenticate: Bearer`, plus `error="invalid_token"` for a bad or expired token |
| Valid token for a user who doesn't exist | 401 problem with the Bearer challenge (`UnknownUserException`) |
| Another user's task | 404, so ids don't reveal existence |
| Title | stripped first, then required and 1–120 characters; description at most 2000; status defaults to `TODO` |
| Due date | not in the past on create; on update only if it changed; "today" in UTC |
| Stale version | 409: the explicit version check, or `@Version` at commit |
| Bad input | malformed JSON, unknown members, unknown status, malformed date, page/size out of range, malformed UUID: 400 problem naming the field |
| Unexpected failure | 500 problem with no message or class name. The stack trace is logged. |
| Filters | `status` and `dueBefore`, in any combination. Order: due date ascending, undated last, then creation time. |

## 4. How this Pokédex was built with AI

The whole project was built with an AI pair (Claude Code), with me in charge of scope, decisions and review. The AI wrote most of the code, tests and documents. The guardrails below are what kept that honest.

The two apps were built in their own repositories, [aleferod/pokedex-api](https://github.com/aleferod/pokedex-api) and [aleferod/pokedex-web](https://github.com/aleferod/pokedex-web), whose pull requests show each change's red/green commits. They were then moved into this repository with their history (`adopt-monorepo`).

### Guardrails

- **Spec first (OpenSpec).** Every change started as `openspec/changes/<id>/` with four files:
  - a proposal (why and what)
  - a design (decisions and trade-offs)
  - a task list with a "Verify:" line per task
  - spec deltas whose requirements have WHEN/THEN scenarios

  `openspec validate --strict` gated each proposal and ran in CI. The archive step, the last commit of each PR, merged the deltas into [`openspec/specs/`](../../openspec/specs): 27 capabilities, 18 for the API, 8 for the web app and one for the repository's layout. When implementation showed a spec or design was wrong, the document was corrected in the same PR, as the examples below show.
- **Test first, and red for the right reason.** Each task pair was a failing `test:` commit (red on assertions, against stubs) and then a `feat:` commit. Every test that passed while still red was inspected, which caught several vacuous tests. Acceptance tests written after the code were mutation-checked: removing `@BatchSize`, the cache Decorator or the retries made them fail.
- **Machine checks over opinions.**
  - `-Werror`, Spotless and JaCoCo (domain and application coverage ≥ 85 %, actually 100 %)
  - ArchUnit layering rules, with a self-test proving each rule catches a broken fixture
  - Testcontainers PostgreSQL and WireMock with real PokeAPI captures
  - gitleaks
- **Docker-only verification.** The whole build ran in containers, as on CI.
- **Checks outside the test suite.** Every change was also checked from a fresh clone with `docker compose up --build` against the real PokeAPI. That run caught things the test suite couldn't, such as the `.gitignore` bug below.
- **A real browser, then end-to-end tests.** Each frontend change was checked by hand in a real browser against a real backend. Those checks found bugs that jsdom couldn't show, such as a sign-out race and a misleading `aria-current`. The last change turned them into Playwright journeys with axe, run against a fresh full stack in CI ([pokedex-web e2e](../../frontend/e2e)).
- **Human checkpoints.** The AI had to stop and ask before anything irreversible or out of scope. Examples:
  - **Spring Boot 4.1:** chosen over the prompt's 3.x because 3.5's open-source support had ended; I approved it (ADR-0006).
  - **409 vs 412:** I chose 409 for a stale `If-Match`, as the brief says, over RFC 9110's 412.
  - **A pasted token:** when I pasted a GitHub token in chat, the AI refused to use it, told me to revoke it, and waited for `gh auth login`.
  - **CI and merges:** I reported CI status and approved each merge.

Two fixes were to the build prompt this project started from, rather than to the AI's code, and were applied before any work began:
- `docker run … node:22-alpine npm ci && npm test` would run `npm test` on the host, not in the container. It became `sh -c "npm ci && npm test"`.
- `git log -p | grep -i token` as the secret check gives false hits on `TokenPort` and JWT code. It became gitleaks plus a grep for real GitHub token prefixes.

Not every problem was the AI's code:
- One finding is still open: Spring Security 7's default `/.well-known/oauth-protected-resource` metadata claims `tls_client_certificate_bound_access_tokens: true`, which this API doesn't support. It's reported, not changed.
- One finding has been fixed since it was recorded. In pokedex-web's forms, a mouse user who clicked a submit button such as **Save** right after leaving an invalid field saw that field's error appear. The error moved the button, so that click didn't submit, and focus reached the first problem only on a second click. It was found while walking [the presentation's demo](../../docs/PRESENTATION.md#the-demo).
  - **The fix** ([`fix-submit-after-blur`](https://github.com/aleferod/pokedex-web/pull/7)): the shared submit button cancels `mousedown`, so pressing it keeps focus in the field and nothing moves before the click lands. An end-to-end test holds the click for 150 ms, as a person does, and failed before the fix.
  - **Not the candidate fix:** the record suggested validating on submit and then on change. That would have dropped the errors shown on leaving a field, such as registration's password rules, and fixed only the forms it was applied to.
- A few were process slips:
  - A scripted multi-file edit stopped halfway on a misread file layout. The script's own assertion caught it, and the edit was re-applied.
  - An archive commit message kept a `<date>` placeholder. It was caught and amended before pushing.
  - Two archive commit messages are wrong. Each was left alone rather than force-pushed, and its pull request's description says so:
